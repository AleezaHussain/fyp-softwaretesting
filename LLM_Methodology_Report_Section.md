# LLM Methodology for the Advisory Assistant

The advisory assistant is a simulation-grounded large language model (LLM) system designed to explain cooling simulation results in plain language. It is not a general chatbot. Instead, it takes a selected simulation, combines it with the user’s question, and generates an answer that stays tied to the simulation context, the project’s methodology notes, and the available model provider.

The workflow begins in the frontend advisory page. The user selects a simulation, types a question, and submits it to the advisory API. The request carries three core inputs: the question text, the simulation ID, and the full simulation object. This ensures the backend always has enough context to generate an informed answer. The page also stores conversation history in browser local storage using a user-specific key, so earlier chats can be reopened later, and it attempts to persist successful conversations to the database for longer-term history.

On the backend, the advisory API first resolves the simulation context. It prefers fetching the simulation from Supabase, but if the database lookup is unavailable it falls back to the simulation payload sent by the frontend. After the simulation is loaded, the backend extracts relevant metrics, such as performance indicators and technique information, and then analyzes the question to detect what the user is asking about. The question is categorized into topics such as energy, cost, thermal behavior, carbon, water, or comparison. The backend also checks whether the user is asking for problems, risks, or drawbacks, because that changes how the LLM is instructed to respond.

Prompt construction is the most important part of the methodology. The backend builds a structured prompt that includes the cooling technique, the question category, and the key simulation results. It can also add a short methodology snippet from the project’s reference files. The system prompt then instructs the LLM to answer directly, use specific numbers, avoid unnecessary jargon, focus on business impact, and remain grounded in the supplied context. If the question is negative or risk-oriented, the prompt tells the model to lead with the worst issue first and avoid overly positive framing. This is a form of prompt engineering that improves relevance and keeps the answer aligned with the user’s intent.

The system uses a provider chain rather than a single model endpoint. Depending on the environment configuration, the backend can route the request to Ollama, xAI/Grok, Groq, OpenRouter, or Gemini. If one provider fails, the backend tries the next one in the chain. If all providers are unavailable, it returns a fallback advisory response instead of failing completely. This failover design improves reliability and keeps the advisory page usable even when external LLM services are temporarily offline.

The response returned to the frontend includes both the generated answer and metadata such as the provider source, model name, provider chain, and simulation ID. The frontend displays this metadata in the conversation view so the user can see which model produced the answer. This makes the advisory feature more transparent and easier to audit.

In summary, the advisory assistant follows a grounded retrieval-and-generation pipeline: simulation context is resolved first, the question is interpreted next, a structured prompt is built, an available LLM provider is called, and the answer is displayed and stored. This design keeps the assistant context-aware and prevents it from behaving like a generic ungrounded chatbot.
