Chapter 3: Methodology

3.1 Chapter Purpose and End-to-End Scope

This chapter documents the complete machine learning recommendation methodology from first principles to deployment behavior. The scope includes: scenario design, simulation-backed label generation, dataset curation, model training, validation, runtime recommendation, explanation generation, and long-horizon impact projection. The objective is not only predictive accuracy, but also operational interpretability and feasibility-aware decision support [28], [29].

The design follows a hybrid paradigm. A supervised classifier predicts a candidate cooling technique from environmental and economic context, while a runtime rule layer validates feasibility and explains trade-offs using actual simulation metrics. This combination improves practical reliability when compared to pure black-box classification [28], [33].

3.2 Formal Problem Definition

The task is modeled as multi-class classification with six predictors and three classes.

f: X -> Y, where X = R^6 and Y = {AirEconomizer, Evaporative, ChilledWater}

Input vector x = [tempC, rh, itLoadKW, electricityPrice, waterPrice, carbonFactor]. Target y = bestTechnique. The model learns decision boundaries that map each operating context to the cooling class with strongest expected performance under constraints [25], [29].

3.3 Assumptions and System Boundaries

  1. The six selected predictors sufficiently represent operating context for technique-level recommendation.
  2. Simulator outputs are treated as ground truth for supervised labels.
  3. Feasibility and violations are hard operational constraints and therefore override purely predictive preference when needed.
  4. Annualized metrics (cost, emissions, water) provide stable planning indicators for recommendation comparison.
  5. The recommendation system is a decision-support tool, not an autonomous control loop.

3.4 Data Sources and Role Separation

The methodology uses two different data streams with distinct roles:

  • Training dataset (CSV): used only to train and validate the machine learning model.
  • Runtime simulation data (database or request): used to construct justification text, comparison table, and future-impact paragraph.

This role separation is central to methodological clarity. Training data teaches the classifier. Runtime simulation metrics explain why a recommendation is currently appropriate.

3.5 Scenario Generation and Label Derivation

3.5.1 Scenario Space

Each row corresponds to one data-center operating scenario containing weather, load, and utility context. For each scenario, all candidate cooling techniques are evaluated.

3.5.2 Simulator Output Variables

  • Annual energy consumption (kWh)
  • Annual operating cost
  • Annual carbon emissions (kg CO2)
  • Annual water usage (liters)
  • Feasibility flag
  • Constraint violation count

3.5.3 Labeling Rule

  1. Evaluate all techniques under identical scenario inputs.
  2. Remove infeasible options or apply violation-aware penalties.
  3. Rank feasible options by weighted multi-metric objective.
  4. Assign top-ranked option as bestTechnique label.

This is simulator-grounded weak-supervision/discriminative labeling rather than manual annotation, which is an accepted approach when stronger oracle outputs are available [25].

3.6 Dataset Construction and Cleaning Workflow

Dataset curation follows strict preprocessing controls to improve quality and avoid leakage [25], [29].

  1. Exact duplicate removal.
  2. Numeric type coercion for all feature columns.
  3. Target normalization and trimming.
  4. Missing-value handling for required fields.
  5. Explicit exclusion of outcome-derived columns from training inputs.
  6. Class distribution check before split and training.

3.7 Train/Test Strategy and Reproducibility Controls

The split strategy uses stratified sampling so all classes remain represented proportionally in both training and testing partitions [26], [33]. Random seed fixation enables repeatable experiments and auditable model comparisons [31].

D_train, D_test = StratifiedSplit(D, test_size = 0.20, random_state = 42)

3.8 Preprocessing Pipeline and Leakage Prevention

Preprocessing is implemented in a single scikit-learn style pipeline to guarantee that transformations learned on training folds are exactly reused on validation and inference data [26].

  • Median imputation for numeric missing values (robust to outliers) [27].
  • Standard scaling for consistent numeric ranges.
  • Pipeline encapsulation to prevent fold contamination during CV.
Leakage prevention is not only feature-column filtering. It also includes procedural control: fit transforms only on training partitions.

3.9 Model Selection Rationale

Random Forest is selected because the relationship between weather/load/economics and best cooling class is nonlinear and interaction-heavy. Tree ensembles naturally capture interaction terms without manual polynomial engineering and remain robust in mixed real-world tabular data [28], [29].

XGBoost is relevant as a strong benchmark family [30], but this implementation prioritizes Random Forest for simplicity, stability, and interpretability-performance balance at FYP scale.

3.10 Hyperparameter Tuning Procedure

Hyperparameter search uses RandomizedSearchCV with stratified 5-fold CV and macro-F1 as optimization objective [26], [32], [33]. Random search is computationally efficient and effective in high-dimensional tuning spaces [32].

3.11 Evaluation Protocol and Quantitative Performance

Evaluation uses both hold-out and repeated-split analysis. Macro-F1 is emphasized to avoid majority-class dominance in interpretation [33].

Metric Result

Held-out Test Macro-F1 0.9207

Mean Macro-F1 (30 repeated stratified splits) 0.9661

Repeated-split testing reduces dependence on a single partition and provides stronger evidence of stability.

3.12 Runtime Inference Pipeline

  1. Receive scenario inputs and hourly arrays.
  2. Aggregate hourly series to scenario-level means for temperature, humidity, and IT load.
  3. Construct feature vector and predict candidate class using trained model artifact.
  4. If per-technique runtime metrics exist, execute feasibility-aware re-ranking logic.
  5. Return final recommendation and explanation payload.
x_runtime = [mean(tempC_hourly), mean(rh_hourly), mean(itLoadKW_hourly), electricityPrice, waterPrice, carbonFactor]

3.13 Feasibility and Composite Scoring Logic

Runtime recommendation uses a constrained ranking strategy. Model output is candidate-level, while final output is feasibility-aware.

S_i = w_c * z(cost_i) + w_e * z(emissions_i) + w_w * z(water_i), with (w_c, w_e, w_w) = (0.50, 0.30, 0.20)
  1. If predicted technique is feasible, keep it.
  2. If predicted technique is infeasible, choose minimum-score feasible alternative.
  3. If all options are infeasible, return prediction with explicit fallback messaging.

3.14 Origin of Justification Paragraphs and Comparison Table

Justification and table outputs are generated from runtime simulation metrics, not from the training CSV.

  • Primary source: simulation records retrieved by simulation ID from Supabase.
  • Fallback source: simulation object provided directly in request payload.

The text generator uses feasibility flags, violation counts, and metric deltas between selected and alternative techniques to produce user reasons. The comparison table is sorted by runtime score and includes annualized cost/emissions/water fields.

Methodological implication: the explanatory narrative is runtime data-grounded and therefore context-sensitive. It is not static templated text disconnected from simulation values.

3.15 Future-Impact Paragraph Logic

Future impact is computed using annual metrics of the selected technique and linear horizon projection for planning simplicity.

Year1 = Annual, Year3 = 3 * Annual, Year5 = 5 * Annual

The projected fields include cost, emissions, and water consumption. This supports budget forecasting and sustainability planning in a transparent and reproducible way.

3.16 Implementation Traceability

The deployed service stack is implemented through validated request schemas, model artifact loading, runtime aggregation, and structured JSON response construction. This traceable implementation path strengthens research reproducibility because each chapter claim maps to executable logic in the system [26], [31].

3.17 LLM Methodology for the Advisory Assistant

The advisory module is implemented as a grounded large language model (LLM) assistant that explains a selected simulation in plain language. Its purpose is not to generate generic text, but to transform the user’s question into a context-aware response based on the active simulation, the extracted metrics, and the project’s internal reference material. The advisory workflow begins when the user selects one simulation, enters a question, and submits it through the chat interface [36], [37].

At runtime, the frontend sends the question, the selected simulation identifier, and the simulation object to the advisory API. The backend then attempts to resolve the simulation context from Supabase first, and falls back to the request payload if the database lookup is unavailable. Once the context is available, the system extracts the key simulation details and constructs a prompt that includes the cooling technique, the relevant performance summary, and any method-specific reference text. This makes the LLM answer anchored to the simulation instead of relying on a general-purpose conversation history.

The prompt-building process also detects the user’s intent. Questions are grouped into categories such as energy, cost, thermal behavior, carbon, water, and comparison, so the response can be framed around the most relevant metrics. If the user asks for risks, weaknesses, or the worst-case outcome, the prompt explicitly instructs the LLM to lead with limitations and negative impacts first. Otherwise, it asks for a balanced explanation that is still practical and decision-oriented. In both cases, the model is told to use specific numbers, avoid jargon, and not mention internal technical details such as simulation IDs or source files.

The backend does not depend on a single LLM provider. Instead, it uses a provider chain that can route the request to Ollama, xAI/Grok, Groq, OpenRouter, or Gemini depending on the environment configuration. If one provider is unavailable, the backend tries the next provider automatically. If no provider can answer, the system returns a safe fallback response that informs the user that live LLM access is unavailable while still acknowledging the selected simulation context. This design improves resilience and prevents the advisory page from failing completely when one model service is offline.

After the model responds, the backend returns both the generated answer and metadata describing the source provider and model used. The frontend displays the message in the conversation thread and stores the chat locally so the user can resume it later. It also attempts to save the exchange into the database for persistence. Methodologically, this creates a complete explainability loop: the simulation is selected, the prompt is grounded in that simulation, the LLM produces a contextual answer, and the result is saved for future review.

3.18 Methodology Conclusion

The final methodology combines simulation-grounded supervision, robust ensemble learning, fairness-aware evaluation metrics, and runtime explainability. It is technically coherent for FYP-level research because it demonstrates full lifecycle rigor: data design, model rigor, deployment logic, and interpretable recommendation output [28], [32], [33], [34].
